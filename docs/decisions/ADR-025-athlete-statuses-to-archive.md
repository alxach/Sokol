# ADR-025: Сведение статусов спортсмена к «Активен» / «В архиве»

## Status
Accepted

## Date
2026-09-02

## Context

[ADR-024](ADR-024-athlete-statuses.md) зафиксировал пять статусов спортсмена
(`active`, `inactive`, `graduated`, `transferred`, `expelled`). Практика показала,
что модель избыточна: статусы `graduated`/`expelled`/`transferred` семантически
пересекаются с `inactive`, заставляя спортивную логику держать списки
`REMOVED_FROM_GROUPS`/`INELIGIBLE_FOR_GROUP` из нескольких значений и вызывая
неоднозначность в интерфейсе (вводящий в заблуждение статус при создании).

Принято решение свести модель к **двум состояниям**:

- `active` — «Активен» (тренируется, входит в составы групп и журнал посещаемости);
- `inactive` — «В архиве» (выведен из всех групп; данные и история соревнований сохраняются).

## Решения

1. **Два статуса.** `AthleteStatus = Literal["active", "inactive"]`.
   Старые значения `graduated`, `expelled`, `transferred` удаляются из модели;
   существующие данные миграцией приводятся к `inactive`
   (миграция `a1b2c3d4e5f6`). Причина выбытия не хранится.
2. **Архив не удаление.** При переводе в `inactive` спортсмен жёстко выводится
   из всех групп (`GroupMemberRepository.remove_all_for_athlete`) и исчезает из
   журнала посещаемости (журнал строится по `GroupMember.is_active = True`),
   но сама запись спортсмена и дочерние данные (документы, мед.карта, история
   разрядов, достижения) сохраняются.
3. **Восстановление.** Перевод обратно в `active` возвращает спортсмена в систему;
   членство в прежних группах НЕ восстанавливается автоматически (hard-delete
   записей `GroupMember`) — состав добавляется вручную.
4. **Нельзя добавить в группу из архива.** `INELIGIBLE_FOR_GROUP = {"inactive"}`:
   `POST /groups/{id}/members` → 422 для «архивных» спортсменов.
5. **Передача тренеру — отдельное действие.** `POST /athletes/{id}/transfer`
   (роли admin/director), тело `{ "new_coach_id": uuid }`. Разрешено только для
   спортсмена со статусом `inactive` (сначала из архива → передать); для `active` → 422.
   Несуществующий спортсмен → 404, несуществующий тренер → 422.
6. **UI создания спортсмена.** Поле статуса скрыто при создании — новый спортсмен
   всегда `active`. Статус выбирается только при редактировании (селект
   «Активен / В архиве»). Для `inactive` в модалке показывается подсказка о
   выводе из групп и возможности восстановления.
7. **Аналитика.** `STATUS_LABELS = {active: "Активные", inactive: "В архиве"}`;
   распределение по статусам становится двухсекторным (детализация — при необходимости позже).
8. **Метрики/отчёты.** Счётчики активных спортсменов (дашборд «Активные»,
   `athletes_count` в отчёте тренера) считают только `status === "active"`.

## Тесты

- `tests/test_athlete_status_groups.py` — архивация убирает из группы, добавление
  архива → 422, `active` остаётся, восстановление, невалидный статус → 422.
- `tests/test_athlete_transfer.py` — передача только архивированного, 404/422
  кейсы, ролевой guard (coach → 403).

## Consequences

- Модель статусов спортсмена стала бинарной: в группе/не в группе, активен/архив —
  без «дыр» между «не тренируется», «отчислен» и «выпустился».
- Потеряна гранулярность причины ухода (были `graduated`/`expelled`); при
  необходимости причина выбытия добавляется отдельным необязательным полем,
  не трогая статус.
- `transferred` исключён из статусной модели: перевод тренеру выполняется
  действием `POST /athletes/{id}/transfer` при статусе «в архиве».
- Существующим данным присваивается `inactive` без сохранения прежнего статуса
  (миграция необратима по своей сути — `downgrade` пустой).

  студент-функциональный тест падает (`total == 2` вместо 3). **Устранено**

  (total считается по своим записям) + autouse-fixture `clean_attendance` в
  `conftest.py` (`DELETE FROM attendance` перед каждым тестом). Полный прогон: 140 passed.
- Браузерный смоук (Chrome MCP, 2026-09-02): создание спортсмена тренером — без
  селекта статуса (создаётся `active`); редактирование — селект «Активен / В архиве»;
  выбор «В архиве» показывает подсказку «Спортсмен будет выведен из всех групп…»;
  статус меняется на «В архиве»; в детали архивного видны «Восстановить» и
  «Передать другому тренеру»; «Восстановить» возвращает `active`; «Передать»
  тренером → 403 «Insufficient permissions» (ожидаемо, роли admin/director);
  суперадмином → 200, тренер в таблице сменяется («Орлов Дмитрий»). Тестовые
  данные удалены, в БД 0 спортсменов. Консоль чистая (только пре-существующий a11y-долг).
