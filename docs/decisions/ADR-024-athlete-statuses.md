# ADR-024: Статусы спортсмена — каноническая модель и связи

## Status
Superseded by [ADR-025](ADR-025-athlete-statuses-to-archive.md) (2026-09-02)

## Date
2026-09-01

## Context

Поле `status` спортсмена (`athletes.status`) долгое время существовало имплицитно:
значения перечислялись в нескольких местах (`AthleteStatus` на бэкенде,
`AthleteStatusKey`/`athleteStatusLabels` во фронтенде, `STATUS_LABELS` в аналитике),
но **единого документа, описывающего статусы, их семантику и все точки использования,
не было**. Это приводило к недопониманию и риску несогласованных изменений
(например, вопрос «где используется „Не тренируется“?»).

Данный ADR фиксирует каноническую модель `AthleteStatus`, связи статуса
с остальной системой (группы, посещаемость, аналитика, отчёты, Excel) и
принятые UX-решения по набору статусов в интерфейсе. Это единый источник правды
для последующих изменений.

## AthleteStatus — пять значений

Системный набор статусов спортсмена (колонка `athletes.status`, тип `String(20)`):

| Значение     | Лейбл (UI)         | Семантика                                       | Влияние на группы/журнал |
|--------------|--------------------|-------------------------------------------------|--------------------------|
| `active`     | Активный           | Тренируется (статус по умолчанию при создании)  | Остаётся в группе        |
| `inactive`   | Не тренируется     | Временная пауза, не уход из системы             | Остаётся в группе и журнале |
| `graduated`  | Выпустился         | Закончил обучение, выбыл                        | Удаляется из всех групп  |
| `transferred`| Переведён          | **Зарезервирован** под будущий перевод тренер→тренер | Технически допустим, но не используется |
| `expelled`   | Отчислен           | Отчислен, выбыл                                 | Удаляется из всех групп  |

Ключевое различие: `active`/`inactive` — «внутренние» состояния (спортсмен остаётся
в составе и журналах), а `graduated`/`expelled` — терминальные состояния ухода
(спортсмен принудительно выводится из всех групп и исчезает из журналов).

`transferred` объявлен в типе и принимается валидацией, но в интерфейсе не
предлагается (зарезервирован под сценарий перевода спортсмена от одного тренера
к другому, который ещё не реализован).

## Где определяется / декларируется тип

- **Бэкенд**: `backend/app/schemas/athlete.py:7` — `AthleteStatus = Literal["active","inactive","graduated","transferred","expelled"]`.
  - `AthleteCreate.status` — по умолчанию `"active"` (строка 22).
  - `AthleteUpdate.status` — опционально, валидируется тем же `Literal` (строка 34):
    невалидное значение → HTTP 422.
- **Фронтенд**:
  - Тип `AthleteStatusKey` и словарь `athleteStatusLabels` —
    `frontend/src/lib/api/athletes.functions.ts:3,70` (все 5 лейблов, включая зарезервированный `transferred`).
  - Набор для **выбора в UI** — массив `statusOptions` в
    `frontend/src/components/athlete-modal.tsx:18`. Сейчас содержит
    `["active","graduated","expelled"]` — **`inactive` и `transferred` в нём отсутствуют**
    (подробнее в «Отображение в интерфейсе»).
  - Стили badge'а — `statusStyle` в `frontend/src/routes/athletes.tsx:59` (все 5).

## Связи: группы и посещаемость

Связь статуса с группами и журналом посещаемости реализована на **бэкенде**
(source of truth) и продублирована на фронтенде для UX-блокировок.

### Бэкенд

- `backend/app/services/athlete_service.py:24` —
  `REMOVED_FROM_GROUPS = {"graduated", "expelled"}`.
- `athlete_service.update()` (строки 64–75): при установке нового статуса в
  `REMOVED_FROM_GROUPS` вызывается `GroupMemberRepository.remove_all_for_athlete(athlete_id)`
  — спортсмен **жёстко (hard-delete)** удаляется из всех `group_members`
  (не soft-leave через `leave_date`, чтобы избежать роста таблицы).
  `member_repo` инжектится через `get_athlete_service` в `app/dependencies.py`.
- `backend/app/services/group_service.py:11` —
  `INELIGIBLE_FOR_GROUP = {"graduated", "expelled"}`.
- `GroupService.add_member()` (строка 61): если у спортсмена статус из
  `INELIGIBLE_FOR_GROUP` → HTTP 422 (нельзя добавить в группу).
- Журнал посещаемости строится по `GroupMember.is_active = True`
  (`attendance_service.py`), поэтому терминальные статусы автоматически убирают
  спортсмена из журналов **без отдельного guard'а на attendance**.
- `inactive`/`transferred`/`active` **не** входят в `REMOVED_FROM_GROUPS` —
  спортсмен остаётся в группе и журнале (проверено тестом `test_athlete_status_groups.py:107`).

### Фронтенд (UX-блокировки)

- `frontend/src/components/athlete-modal.tsx:25` —
  `LEAVES_GROUPS = ["graduated","expelled"]`; при выборе такого статуса под селектом
  показывается подсказка «Спортсмен будет удалён из всех групп и исчезнет из журнала посещаемости».
- `frontend/src/routes/groups.tsx` (форма создания/редактирования состава):
  спортсмен со статусом `graduated`/`expelled` — чекбокс `disabled` + лейбл
  «Отчислен»/«Выпустился»; в `AddAthleteModal` такие спортсмены отфильтрованы из списка кандидатов.

| Таблица спортсменов | `routes/athletes.tsx:379–380` | Badge-бейдж: цвет из `statusStyle`, текст из `athleteStatusLabels` |

| Служебная строка реестра | `routes/athletes.tsx:162` | `athleteStatusLabels[...]` |

### Аналитика (backend → frontend)

- `backend/app/services/analytics_service.py:13–19` — `STATUS_LABELS` (все 5, включая «Не тренируется» и «Переведён»).
- `analytics_service.py:254` — агрегация `GROUP BY Athlete.status` → `athletes_by_status`.
  Категория «Не тренируется» (`inactive`) попадает в pie-chart распределения по статусам
  на дашборде admin/director (`GET /analytics/summary`).
- Фронтенд пай-чарта: `routes/analytics.tsx` (поле `athletes_by_status` из `fetchAnalyticsSummary`).

### Отчёты (backend)

- `athletes_count` в отчёте тренера на **фронтенде** считает только `active`
  (`routes/reports/new.tsx:237–242`, фильтр `a.status === "active"` + возраст ≤ 21).
- На бэкенде поле `athletes_count` отчёта не зависит от `Athlete.status` напрямую —
  считает по нормам шаблона из групп и возраста автора.

### Экспорт Excel

- `backend/app/services/excel_export_service.py:51` — строка экспорта спортсмена
  содержит сырое значение `a.status` (одно из 5). Импорт принимает «статус»
  по свободной строке без строгой валидации набора (свободное поле).

### Тесты

- `backend/tests/test_athlete_status_groups.py` — 6 тестов: добавление
  `graduated`/`expelled` → 422; смена на `expelled`/`graduated` удаляет из группы;
  `active`/`inactive`/`transferred` оставляют в группе (строки 107–119); невалидный статус → 422.

## Решения по UX (UI-набор статусов)

Селект статуса в `athlete-modal.tsx` (`statusOptions`) — это **UI-видимая подмножество**,
а не полный канонический набор. Текущее состояние и обоснования:

- **`active`, `graduated`, `expelled`** — предлагаются в селекте.
- **`inactive` («Не тренируется») убран из селекта** (решение 2026-09-01): при
  добавлении нового спортсмена статус по умолчанию `active`; предложение «Не тренируется»
  в момент создания вводит тренера в заблуждение (нового спортсмена добавляют как активного).
  Значение `inactive` **остаётся валидным в системе** (`Literal`, `STATUS_LABELS`,
  `athleteStatusLabels`, бейдж в таблице, pie-chart) и корректно отображается
  для уже существующих записей. Выставить его напрямую через UI сейчас нельзя;
  при необходимости — только через API/PATCH.
  - Edge-кейс редактирования: если у спортсмена уже стоит `inactive` и тренер открывает
    модалку редактирования, селект обязан показать текущее значение (иначе визуально
    «съедет» на «Активный»). Это обеспечивается показом «закрытой» опции текущего статуса,
    когда он не входит в `statusOptions`.
- **`transferred` («Переведён») убран из селекта** (ранее, в модуле связки
  статус↔группы): зарезервирован под будущий сценарий перевода тренер→тренер.
  В типе сохранён (не удаляется из `Literal`/`StatusKey`), в UI не предлагается.

Итоговый принцип: **тип/система допускает все 5 значений** (для целостности данных и
обратной совместимости), но интерфейс сознательно предлагает только актуальные для
тренера статусы (`active`, `graduated`, `expelled`) и скрывает `inactive` и `transferred`
до появления соответствующих бизнес-процессов.

## Consequences

- Единый источник правды для статусов спортсмена — дальнейшие изменения согласуются
  с этим документом.
- `inactive` и `transferred` остаются в системе, но не предлагаются в UI — если позже
  потребуется «временная пауза» через интерфейс, достаточно вернуть `inactive` в
  `statusOptions` (с учётом guard'а на редактирование).
- Терминальные статусы (`graduated`/`expelled`) жестко связаны с группами/журналом —
  изменение этой связи требует пересмотра и `athlete_service.REMOVED_FROM_GROUPS`,
  и `group_service.INELIGIBLE_FOR_GROUP`, и фронтовых блокировок.

## Notes

- Документ охватывает только статус **спортсмена** (`athletes.status`). Статусы других
  сущностей (тренера, расписания, отчётов, планов, посещаемости, соревнований,
  протоколов комиссии) — вне рамок; при необходимости им требуется отдельный ADR.
- Сопутствующее (справочник разрядов, дефолт «Без разряда») документировано в roadmap.md
  и не относится к статусам.
