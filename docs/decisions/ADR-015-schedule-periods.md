# ADR-015: Расписание с периодами действия и утверждением

## Status
Accepted

## Date
2026-06-28 (v1) · 2026-07-07 (v2) · 2026-07-15 (v3) · 2026-07-15 (v4)

## Context
Расписание тренировок в текущей реализации — плоский список занятий без привязки к датам. Тренер создаёт занятие на день недели, но нет:
- **Срока действия** — расписание действует бесконечно, нельзя задать период (например, 8 месяцев)
- **Статуса** — нельзя отличить черновик от утверждённого расписания
- **Редактирования** — нельзя изменить существующее занятие, только удалить и создать заново

Требуется:
1. Тренер создаёт расписание на период (например, 8 месяцев)
2. Утверждает его (переводит в active)
3. По истечении периода расписание становится archived
4. Полноценный CRUD для занятий внутри периода
5. Управление расписанием как на странице `/schedules`, так и в деталях группы `/groups`

### v3 (2026-07-15): Проблема дублирования entry points

Анализ показал, что создание периода расписания доступно из **двух мест** с разным UX:
- `/groups` — контекст группы уже известен, модалка без селектора группы
- `/schedules` — группа неизвестна, модалка с селектором группы

Это приводит к:
- Дублированию ~200 строк кода (CreatePeriodForGroupModal vs CreatePeriodModal)
- Когнитивной нагрузке: непонятно, где создавать
- Различиям в реализации: escape/click-outside, toast, autofocus только в одном из двух
- Дублированию CRUD-операций (approve/delete) с различающейся логикой

**Решение**: создание расписания — **только через `/groups`** (Group-first flow). Страница `/schedules` — **только просмотр**.

### v4 (2026-07-15): UX карточек, архивация, дублирование, отпуска

**Проблемы:**
1. Карточки периодов на `/scales` содержали кнопки «Изменить» и «Удалить» — дублировали CRUD из детального вида
2. Удаление периода безвозвратно удаляло данные — потеря истории расписаний
3. При переходе на новый учебный год тренер вынужден вручную переписывать расписание для каждой группы
4. Отпуска и больничные тренера не отображались в расписании — непонятно, будет ли тренер доступен

**Решения:**
1. **Карточка — навигация**: кнопки «Изменить» и «Удалить» убраны с карточки. Карточка — чистый entry point в детальный вид
2. **Редактирование в detail view**: кнопки «Изменить период», «Удалить», «Дублировать» — в хедере `PeriodDetailView`
3. **Удаление = архивация**: `handleDeletePeriod` ставит `status = "archived"` вместо удаления из массива. AlertDialog показывает детали периода (группу, даты, кол-во занятий) и поясняет архивацию
4. **Дублирование периода**: `duplicatePeriod(sourcePeriodId)` — создаёт новый draft-период с датами +1 год, копирует все `Schedule` занятия. Кнопка `Copy` в хедере detail view
5. **Отпуска/больничные в расписании**: в `PeriodDetailView` для каждого дня недели проверяется попадание в `vacations`/`sickLeaves` тренера. Бейджи «Отпуск» (warning) / «Больничный» (destructive) отображаются в заголовке дня

## Decision

### Модель данных
Вводится нормализованная модель: `SchedulePeriod` (период) → `Schedule` (занятия).

```typescript
interface SchedulePeriod {
  id: string;
  coachId: string;
  coachName: string;
  group: string;          // Group.name (связь по имени)
  discipline: Discipline;
  periodStart: string;    // "2026-01-01"
  periodEnd: string;      // "2026-08-31"
  status: "draft" | "active" | "archived";
  createdAt: string;
}

interface Schedule {
  id: string;
  periodId: string;       // FK → SchedulePeriod.id
  dayOfWeek: number;      // 1=Пн … 7=Вс
  timeStart: string;
  timeEnd: string;
  room: string;
}
```

### Workflow утверждения
1. Тренер создаёт период (черновик, `status: "draft"`)
2. Заполняет занятия внутри периода
3. Нажимает «Утвердить» → `status: "active"`
4. При утверждении нового периода для группы, у которой уже есть активный период, старый автоматически переводится в `archived`
5. При наступлении `periodEnd < today` → период считается `archived`
6. Archived — read-only. Active — редактируется с подтверждением (AlertDialog: «Вы уверены? Изменение затронет утверждённое расписание»).

### Страница `/schedules` (только просмотр)
- Список периодов (карточки) — основное представление
- Клик по периоду → детальный просмотр с сеткой дней
- Внутри детального просмотра: CRUD занятий (создание, редактирование, удаление)
- В пустых днях — кнопка «+ Добавить» с предустановкой дня недели в форме
- Кнопка «Утвердить» для draft-периодов
- Фильтрация по статусу (все / активные / черновики / архив)
- Под карточками периодов — сквозная сетка «Неделя»: day grid со всеми занятиями из видимых периодов (read-only, для обзора)
- **Нет** кнопки создания периода — создание только через `/groups`

### Страница `/groups` (единственный entry point для создания)
- В деталях группы — список периодов расписания для этой группы
- Кнопка «+ Добавить период» → `CreatePeriodForGroupModal` (groupId/discipline предзаполнены из контекста группы)
- У каждого периода — даты, статус, количество занятий
- Управление занятиями внутри периода (CRUD)
- Редактирование/удаление только для draft-периодов

### Дашборд `/`
- `mySchedulesToday` фильтрует только по **active** периодам, у которых `periodStart <= today <= periodEnd`

### Персистентность (мок-фаза)
- `schedulePeriods` и `schedules` хранятся в памяти и сохраняются в localStorage
- Автоматическая загрузка/сохранение при мутациях
- `archived` вычисляется динамически: если `periodEnd < today`, период показывается как archived

## Alternatives Considered
- **Плоская модель (status/periodDates прямо в Schedule)**: проще, но приводит к дублированию данных — для каждого дня недели пришлось бы повторять период действия и статус. Нормализованная модель чище.
- **Авто-утверждение при создании**: лишает тренера возможности подготовить расписание заранее и утвердить после проверки.
- **Только просмотр, без управления на /groups**: пользователю пришлось бы переключаться между страницами.
- **v3: Два entry point'а для создания периода (/groups + /schedules)** — rejected. Дублирование ~200 строк, различающийся UX, когнитивная нагрузка. Group-first flow (/groups) естественнее для тренера.

## Consequences
- При утверждении нового периода старый активный период той же группы автоматически архивируется (гарантируется не более одного active периода на группу)
- В модалках создания периода показывается предупреждение, если у группы уже есть активный период
- Все существующие Schedule получают `periodId` — для обратной совместимости создаётся один период на группу
- Связь с группой теперь по `groupId` (а не по `group.name`). Переименование группы не ломает расписание.
- При перезагрузке страницы данные восстанавливаются из localStorage
- ADR-005 (разное время для каждого дня) остаётся в силе — внутри периода занятия создаются по той же логике
- **Защита от случайных изменений**: удаление периода или занятия всегда требует подтверждения (AlertDialog). Добавление/редактирование в active-периоде — через AlertDialog с предупреждением. Для draft — без подтверждения.
- **v3**: Создание периода расписания — **только через `/groups`**. Страница `/schedules` — только просмотр и управление существующими периодами. Убран `CreatePeriodModal` (~200 строк) и кнопка «Создать расписание для группы» со страницы `/schedules`.
- **v4**: Карточки периодов — навигация (без CRUD-кнопок). Редактирование/удаление/дублирование — только в `PeriodDetailView`. Удаление = архивация (soft delete). `duplicatePeriod()` создаёт draft с датами +1 год и копирует занятия. Отпуска/больничные тренера отображаются бейджами в сетке дней.

## Notes
Сейчас `Schedule.group` и `Schedule.discipline` дублируют данные из `SchedulePeriod`. В перспективе, при переходе на нормализованную связь по Group.id, эти поля можно убрать из Schedule.
